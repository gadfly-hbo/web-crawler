# 红队审查：web-crawler 三维矩阵演进方案审查

## 1. 核心假设与承重墙分析

1. **假设 1：大量数据源可以通过通用的声明式 JSON 配置完成采集**
   - **脆弱点**：现实中许多网站有动态验签（如 `sign = md5(timestamp + salt + body)`）或滑动验证码，纯静态配置无法计算动态签名。
   - **对策与边界**：明确声明式 API 连接器的边界——专注于处理标准 REST/JSON API（支持 Bearer Token、Cookie、API Key、静态 Header），不强行在配置中堆砌复杂的 JS 运行沙箱；复杂的动态反爬留给第 3 维（Agent 浏览器自动化）解决。

2. **假设 2：多态 TaskParams 不会破坏现有 tasks.json 历史任务持久化**
   - **脆弱点**：存量 `data/tasks.json` 中已保存的历史任务均不含 `sourceType` 属性，若直接假设 `sourceType` 必填，会导致启动反序列化失败或历史任务无法查看。
   - **对策**：契约中 `sourceType` 设为可选，所有读取与分发逻辑遵循 `const type = task.params.sourceType ?? 'cninfo'`，100% 保证存量历史任务向后兼容。

3. **假设 3：通用分页配置可能陷入无限循环**
   - **脆弱点**：用户若配错 `hasMorePath` 或源站接口未返回明确结束标志，爬虫可能无休止请求导致死循环或被封禁。
   - **对策**：内置防御性熔断机制——强制设定 `maxPages` 上限（默认 50，单任务最多 200），翻页到达上限强制安全结束并提示用户；同时保留全局最低 `sleepMs >= 200` 频控保护。
