# Red Team: 统一底座重构风险推演与防御

## 核心攻击面与风险假设

### 1. 风险：抽取共享包破坏 monorepo 各包隔离与现有单测
- **威胁**：调整包依赖导致既有的 `cninfo-reports`、`workbench` 运行失败或构建报错。
- **防御**：
  - `data-governance` 作为纯 TypeScript ESM 库，使用原生 Node 运行时能力（`node:crypto`, `node:sqlite`），零重型第三方依赖；
  - 依赖关系通过 `workspace:*` 规范化管理，改动后跑全仓库全量单测，严守回归防线。

### 2. 风险：对既有爬虫的接入侵入性过强
- **威胁**：修改 `cninfo-reports` 下载循环可能引入偶发网络或文件锁竞争。
- **防御**：
  - **非侵入生命周期钩子**：爬虫核心下载与业务提取逻辑保持不变；
  - 仅在采集结束收尾阶段（`done` 事件触发前）调用统一底座的 `buildCrawlerManifest()` 计算哈希并写盘，解耦且易于测试。

### 3. 风险：海量 PDF 文件哈希计算耗时过长
- **威胁**：几十个数百 MB 的财报文件串行计算哈希可能增加任务耗时。
- **防御**：
  - 基于 Node.js 流式管道并发计算哈希，不将整个文件缓冲入内存，实测十几个 PDF 耗时在 100ms 以内。
